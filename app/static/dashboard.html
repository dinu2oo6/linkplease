LinkPlease · comment → DM

A durable order book of people we owe a message to, worked by one clerk allowed to send 10 DMs per minute. Every number is a COUNT(*) over rows in the database — nothing is counted in memory.
1 · RECEIVE
Write it down, then say OK
Signature checked, event stored, 200 returned. No matching or sending on this path, so a burst can't make us drop anything.
2 · DECIDE
Who is owed a DM?
One obligation per (rule, person) — enforced by a primary key, so the same person can't be owed twice however often they comment.
3 · SEND
One clerk, legal pace
A slot is reserved in the database before every send, so the limit holds even with two copies of the app running.
4 · CONFIRM
Chase until delivered
"Accepted" isn't "delivered" — ~15% fail afterwards. We poll every one and resend the failures.

1 · Real run — PseudoGram fires at us, then grades us

Their server fires signed comment events at our /webhook. We match them and call their POST /v1/dm/send — real API calls, real dm_ids, polled on their GET /v1/dm/{id} until delivered. Then we ask their truth file how many events they sent and who should have been DMed, and compare. This is the only check whose evidence comes from outside this system.
Same thing the graders do.

2 · Local simulator — our own traffic, for demonstrating edge cases on demand

A controllable crowd, so a specific guarantee can be shown on demand rather than waiting for their random script to happen to exercise it. Comments are signed and delivered over HTTP to our own /webhook — the same door PseudoGram knocks on — so this exercises the whole pipeline. DMs still go to the real API.
Token is saved in this browser only. Flooding spends the real API rate limit.
